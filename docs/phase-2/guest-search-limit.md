# Guest Search Limit ("3 Free Searches")

15 Nov 2026. Implemented on `feature/phase-1-platform-foundation`. **Not live yet:** it needs
one migration applied and two server-side variables set (section 11). Until then the Directory
search works exactly as before, with no limit.

## 1. Product rule

| Who                     | Rule                                                                                    |
| ----------------------- | --------------------------------------------------------------------------------------- |
| Visitor without account | 3 Directory searches per UTC calendar day. The 4th is refused before the search runs    |
| Signed-in user          | No limit                                                                                |
| Browsing                | Never limited: tools, categories, guides, prompts, workflows, comparisons, detail pages |
| AutoFlow                | Unchanged: application routes need login                                                |

### What counts

| Counts as one search                                                                   | Does not count                                       |
| -------------------------------------------------------------------------------------- | ---------------------------------------------------- |
| Submitting the main search field (header, Directory home, search page, not-found page) | Typing; suggestions                                  |
| Choosing a suggested search                                                            | Reloading or going back to results (same request ID) |
| A search with zero results                                                             | Changing the result-type tab                         |
|                                                                                        | Category navigation, list filters, sorting, paging   |
|                                                                                        | Any page view                                        |
|                                                                                        | A request refused for validation                     |
|                                                                                        | A retry of the same request ID                       |

The keyword boxes on the tool, prompt and workflow list pages are list filters and are not
counted. See limitation 3.

## 2. How one search flows

```
submit ─► client makes a request ID ─► /search?q=…&rid=<uuid>
            page sends   POST /api/directory/search { query, request_id }
server:   validate ─► verified session?  yes ─► search, access.type = authenticated
                                         no  ─► verify or create signed guest cookie
                                                database: consume_guest_search(hash, request_id, address hash)
                                                   allowed ─► run the existing Directory search ─► 200
                                                   refused ─► 429, search never runs
```

Loading `/search?q=…` without a request ID runs nothing; the page asks the visitor to press
Search. This is what stops reloads, shared links and link prefetching from using searches.

## 3. API contract

`POST /api/directory/search`, JSON body:

| Field        | Rule                                                              |
| ------------ | ----------------------------------------------------------------- |
| `query`      | String, 1–100 characters after trimming and collapsing whitespace |
| `request_id` | UUID generated by the client for this submission                  |

Body limit 2 KB. Anything else in the body is ignored, including any user or guest identifier.

| Status | Body                                                                                                    |
| ------ | ------------------------------------------------------------------------------------------------------- |
| 200    | `{ query, results: [{ type, title, description, href, context?, skillLevel?, isSample }], access }`     |
| 400    | `{ error: { code: "INVALID_REQUEST", message } }` — uses no search                                      |
| 429    | `{ error: { code: "GUEST_SEARCH_LIMIT_REACHED", message }, access }` with `remaining: 0` and `reset_at` |
| 429    | `{ error: { code: "GUEST_SEARCH_RATE_LIMITED", message }, access }` — address cap (section 8)           |
| 503    | `{ error: { code: "SEARCH_UNAVAILABLE", message } }` — the limit could not be checked                   |

`access` for a visitor: `{ type: "guest", enforced, limit: 3, used, remaining, reset_at }`.
`access` for a signed-in user: `{ type: "authenticated" }`, with no counter.

`GET /api/directory/search` returns `{ access }` for the counter. It uses nothing and creates no
cookie. All responses are `Cache-Control: private, no-store`.

Results come from the existing `searchContent()`; matching and ranking are unchanged.

## 4. Guest identity

| Step         | Detail                                                                                                               |
| ------------ | -------------------------------------------------------------------------------------------------------------------- |
| Create       | 32 random bytes from the server's cryptographic generator, on a guest's first search                                 |
| Sign         | HMAC-SHA-256 with `GUEST_SEARCH_SECRET`                                                                              |
| Cookie       | `akf_guest=<id>.<signature>`; HttpOnly; Secure in production; SameSite=Lax; Path=/; 180 days                         |
| Verify       | Every guest search re-computes the signature (constant-time compare)                                                 |
| Bad cookie   | Missing, altered, forged or signed with another secret: ignored and replaced by a new identity                       |
| Store        | The database gets `HMAC(secret, id)` as 64 hex characters. The identifier itself is never stored, logged or returned |
| Not accepted | Guest identifiers in the body, query string or headers                                                               |

This identifies a browser, not a person. Clearing cookies or using another browser gives a new
identity and three more searches.

## 5. Database (migration `0008_guest_search_limit.sql`)

| Object                                                 | Purpose                                                                                                      |
| ------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------ |
| `guest_search_usage`                                   | One row per guest hash per UTC day; `search_count` 0–3 (check constraint); unique `(guest_hash, usage_date)` |
| `guest_search_requests`                                | Processed request IDs with their answer, for idempotent retries                                              |
| `guest_search_ip_usage`                                | Accepted guest searches per hashed address per day                                                           |
| `consume_guest_search(hash, request_id, address_hash)` | The atomic operation                                                                                         |
| `guest_search_status(hash)`                            | Read-only usage for the counter                                                                              |

No query text is stored. Rows are deleted when they are no longer needed (requests after 1 day,
counters after 7).

Security: row level security is on for all three tables with **no policies**, and all table
privileges are revoked from `anon` and `authenticated`. Both functions are `security definer`
with a fixed search path, and `execute` is revoked from `public`, `anon` and `authenticated` and
granted to `service_role` only.

### Atomic enforcement

Inside one transaction `consume_guest_search`:

1. Takes a per-guest advisory lock.
2. Reads the date from the database clock (`now() at time zone 'utc'`).
3. If the request ID was already processed today, returns that answer and changes nothing.
4. Checks the address cap.
5. Increments with one statement: `insert … on conflict … do update set search_count =
search_count + 1 where search_count < 3`. If no row comes back, the limit is reached.
6. Records the request ID and returns `allowed`, `used`, `remaining`, `reset_at`.

Step 5 alone cannot pass 3 under concurrency; the check constraint is a second guard.

## 6. Reset

The boundary is the UTC calendar day, from the database clock. A new day simply uses a new row;
there is no timer or job. `reset_at` is the next UTC midnight, shown in the visitor's local time.

## 7. Interface

| State            | What the visitor sees                                                                                                                                                                                            |
| ---------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Guest, unused    | "Free searches remaining 3/3" under the main search field                                                                                                                                                        |
| After a search   | 2/3, then 1/3 in amber with "Last free search today."                                                                                                                                                            |
| None left        | 0/3 in red, the reset time, and a link to create an account                                                                                                                                                      |
| 4th search       | No results. Dialog: "You've used all 3 free searches today." / "Create a free AIKitFinder account to continue discovering AI tools." / **Create Free Account** / "Already have an account? Sign in" / reset note |
| Dialog dismissed | The page shows the same message with both actions and links to browse                                                                                                                                            |
| After sign-in    | Returns to the same search address; the search runs once, with no quota used                                                                                                                                     |
| Signed in        | No counter                                                                                                                                                                                                       |
| Loading, error   | Announced placeholder (no animation under reduced motion); plain error message                                                                                                                                   |

The dialog is the existing shared account dialog with a different heading, so there is one
sign-in system. The counter is a polite live region; the dialog traps focus and closes on Escape.

The counter and page use the Directory's existing tokens. The approved teal-navy Directory
identity has not been applied to the Directory yet; when it is, these inherit it.

## 8. Abuse controls and their limits

| Control                          | Detail                                                                  |
| -------------------------------- | ----------------------------------------------------------------------- |
| Server-side enforcement          | The browser decides nothing                                             |
| Atomic count, idempotent retries | Section 5                                                               |
| Input limits                     | 100-character query, 2 KB body, UUID request ID, JSON only              |
| Per-address daily cap            | 60 accepted guest searches per address per UTC day (20 full allowances) |
| Double submit                    | Ignored while a submission is in progress                               |

Known limits, stated plainly:

1. **Cookies can be cleared.** A visitor who clears cookies gets three more searches, up to the
   address cap.
2. **The address cap is coarse.** It uses a hashed address, resets daily and never blocks
   permanently. A large shared network could reach it; those visitors are asked to sign up. A
   visitor who changes networks avoids it.
3. **List-page keyword filters are not counted.** `/tools?q=…` and the similar boxes on the
   prompt and workflow lists filter a list and are treated as filters. They let a visitor look
   up tools by name without using a search. Counting them is a product decision for the owner.
4. **No short-window throttle.** There is no per-second limit in the app; there is no Redis.
   Vercel's platform protections apply.
5. **If the quota check fails** (database unreachable), guest search returns 503 rather than
   running unmetered.

## 9. Environment variables

| Variable              | Where       | Purpose                                        |
| --------------------- | ----------- | ---------------------------------------------- |
| `GUEST_SEARCH_SECRET` | Server only | Signs the guest cookie. At least 32 characters |
| `SUPABASE_SECRET_KEY` | Server only | Lets the server call the two quota functions   |

Generate the first with `openssl rand -base64 48`. The second is the key starting `sb_secret_`
in Supabase → Project Settings → API Keys. Neither has a `NEXT_PUBLIC_` prefix, and neither is in
the repository.

This is the first server-side secret the app holds. `src/lib/supabase/service.ts` is marked
server-only and is used for these two function calls and nothing else; user data still goes
through the signed-in user's own client and row level security.

With either variable missing the limit is **off** and search behaves as before.

## 10. Privacy and analytics

No analytics system exists in the repository. The server writes one structured log line per
event with a name and a time only: `guest_search_allowed`, `guest_search_limit_reached`,
`guest_search_rate_limited`, `authenticated_search`, `directory_search_executed`,
`directory_search_unavailable`. No cookie, hash, address, user ID or query text is logged.
`guest_signup_after_limit` is not recorded: it needs an analytics store to connect the two
moments, and none exists. No fingerprinting is used.

1. **Apply migration 0008** to the Supabase project. It is additive. (Needs owner approval; the
   standing rule is no production database change without it.)

3. **Redeploy.**
4. **Verify:** `GET /api/directory/search` returns `"enforced": true`; three searches work and
   the fourth opens the dialog.

503 until it is.

Remaining notes, none blocking:

- The per-address cap is read and then written without a shared lock, so simultaneous guests on
  one address can pass 60 by a few. It is a soft abuse control, not a quota.
- The cap trusts the address header set by the host. Vercel overwrites it; behind a different
  proxy it would need review.
- Cleanup runs inside every accepted search. It is three indexed deletes and is cheap at this
  scale; a scheduled job would be the better home if volume grows.
- A hashed address kept for up to 7 days is pseudonymous personal data. The privacy policy
  should mention it when that page is written.
- The functions from migration 0006 (already applied) use `search_path = public` without
  `pg_temp`. They are trigger functions and cannot be reached with a temporary table through the
  API, so the risk is low, but a small follow-up migration would align them.

### E. Rate limiting

Today: 3 per guest per day, and 60 accepted guest searches per hashed address per day.

What the daily cap does not cover: a flood of requests. Every request, including refused ones,
makes one database call, and nothing limits how fast they arrive. Signed-in users have no cap at
all. Search is cheap today (in memory over sample data) but will become a database query.

A short-window throttle is **recommended before real traffic, not required to switch the limit
on**. Without Redis or a paid service, in order of preference:

1. **Vercel Firewall rate-limit rule** on `POST /api/directory/search` (for example 20 per
   minute per address). No code; it stops requests before they reach the app or the database.
   Whether the current Vercel plan includes it needs checking.
2. **In-process limiter** in the route, in front of the database call: a small in-memory window
   per hashed address. Free and immediate, but per server instance, so on serverless hosting it
   is best-effort only.
3. **Database window**: a per-address, per-minute counter inside `consume_guest_search`.
   Accurate across instances, but every refused request still costs a database call.

Recommendation: option 1 if the plan allows it, otherwise option 2 now and option 3 only if
abuse is seen. A per-user daily ceiling for signed-in accounts should come with the credits
system.
